# Plan — from the dashboard to a real desktop dashboard

**Status:** proposed, awaiting approval. Nothing below is built.
**Scope:** four slices, in order. Each ends green. No slice mixes a refactor with a feature.

---

## Where this starts

The dashboard itself is done — Variant A, over the in-memory books in `web/books`.
Its figures are computed correctly and its storage is a test fixture: enter a
document, restart, it is gone.

Two facts decide everything below:

1. **`internal/reports` cannot read MariaDB at all.** Its `Journal` port
   (`Lines(ctx, from, to)`) has exactly one implementation — the in-memory
   `journalSource` in `web/books`. `db/queries/gl.sql` can read the lines of
   *one* voucher (`ListVoucherLinesByVoucherID`) and nothing else. So no report —
   trial balance, P&L, balance sheet — can be computed from real books today.
   Since every dashboard figure *is* a report, this is the blocker.

2. **`web.Server` is unmounted.** ADR 0004 named the mount as the next slice.

There is also a duplicate to retire on the way: `practice.Client.TrialBalance`
runs its own `SELECT ... GROUP BY a.code, vl.side` over posted lines — no period,
no per-row voucher tracing, no `SourceVoucherCount`. A second, quieter copy of a
rule `internal/reports` already owns with guarantees.

## The one seam

Every slice hangs off a single port, already declared:

```go
// internal/reports/reports.go
type Journal interface {
    // Both ends inclusive, compared by calendar day. A zero `from` means the
    // beginning of the books, which is what a balance sheet asks for.
    Lines(ctx context.Context, from, to time.Time) ([]Line, error)
}

type Line struct {
    VoucherID   string
    VoucherDate time.Time
    AccountCode string
    Side        gl.EntrySide
    Amount      decimal.Decimal
}
```

`NewService(periods Periods, journal Journal, chart ledger.ChartSource, closing ClosingAccounts)`.

`practice.Client.Chart` matches `ledger.ChartSource` exactly. `reports.Periods`
needs a one-line wrapper, because the port names that method `List` and the client
names it `Periods`. `Journal` is the only port with no implementation at all —
which is the whole of Slice 1.

## Slice 1 — a MariaDB ledger source for `internal/reports`

**Why first:** shortest path to a real dashboard. It turns on the four figures and
the three report screens at once, and makes the duplicate trial balance retirable.

| File | Change |
| :--- | :--- |
| `db/queries/gl.sql` | add `ListPostedLinesInRange :many` — `voucher_lines` ⋈ `accounts` (for the code) ⋈ `vouchers`, `v.is_posted = TRUE`, `voucher_date` in range, ordered by date then `line_order` |
| `internal/adapter/mariadb/sqlc/*` | regenerated by `sqlc generate` |
| `internal/adapter/mariadb/ledgerrepo/` | new package: `Source` implementing `reports.Journal` (the query), plus wrappers delegating `Periods` and `Chart` to `practice.Client` |
| `internal/usecase/practice/client.go` | add `func (c *Client) DB() *sql.DB` — so the adapter shares the one pool instead of opening a second to the same database |

Additive throughout: a new query, a new package, one new method. No existing
signature moves. `sqlc generate` rewrites generated files — expected, and approved
by approving this plan.

Implementation detail the port demands: a **zero `from`** means "from the
beginning of the books". Translate it to a floor date rather than emitting a
`>= NULL` comparison, which would silently return nothing and make every balance
sheet read as if the client had never traded.

**Acceptance evidence:** `ledgerrepo` integration test on a real MariaDB
(`fingo_test_*`). Post one set of entries, then compute the trial balance, P&L and
balance sheet twice — once through the MariaDB source, once through the in-memory
`web/books` source — and assert the reports are identical row for row, figure for
figure, `SourceVoucherCount` included. Two implementations of one port, cross-checked
against each other rather than against numbers typed into the test.

**Gate:** `gofmt` · `go build ./...` · `go vet ./...` · `go test ./...`.

## Slice 2 — VAT rates get a table

**Why separate:** it is a schema change, which is its own tier. Migration 00014
already records the gap in a comment: *"`vat_rate_id` at a rate table that does
not exist yet — `internal/vat` holds the registry in memory."* Until a table
exists, `web.Books.Settings` and `CreateVATRate` cannot come from storage, so
Slice 3d is blocked on this.

| File | Change |
| :--- | :--- |
| `db/migrations/00016_vat_rates.sql` | `vat_rates(id, rate_basis_points, effective_from, effective_to NULL, client_id)`, goose-marked |
| `internal/adapter/mariadb/vatrepo/` | append-only store: one active rate per date, no update path — the registry's own rule, enforced in the adapter |

**Acceptance evidence:** integration test that inserts two overlapping windows and
asserts the second is refused, and that a rate read back equals what `internal/vat`
accepted in memory for the same input.

**Hazard to note, not fix:** `internal/migrate.Load` refuses a set that is not
`1, 2, 3 …` with nothing missing, and `db/migrations` has no `00006`. That runner
can therefore never adopt this directory as it stands. Unrelated to this plan —
but it must not be wired to `db/migrations` by accident.

## Slice 3 — `web.Books` over MariaDB

**This is not one slice.** It decomposes by screen, each ending green. The
acceptance criterion is the same for all of them and is the payoff of having a
port at all: **the existing `web` e2e suite runs unchanged against the MariaDB
implementation.** The pages do not move; only the thing behind them does.

| | Sub-slice | Backing that already exists |
| :--- | :--- | :--- |
| 3a | `Dashboard`, `TrialBalance`, `ProfitAndLoss`, `BalanceSheet` | Slice 1 |
| 3b | `Accounts`, `CreateAccount` | `ListAllAccounts`, `CreateAccount` (already in `gl.sql`) |
| 3c | `Documents`, `Document`, `CreateInvoice`, `CreatePayment`, `CreateJournal` | `arap_documents` + `documentstore`; `internal/trading` is the flow to route through |
| 3d | `Settings`, `CreatePeriod`, `CreateVATRate` | Slice 2; `periodstore` + `practice.CreatePeriod` |

3a alone makes the dashboard's four figures real — it is the milestone, not the
end of the slice.

**Acceptance evidence:** `web`'s existing tests parameterised over two `Books`
implementations. If a page passes in memory and fails on MariaDB, the port is not
honoured and the adapter is wrong — which is exactly what a port is for.

## Slice 4 — mount it in the desktop app

| File | Change |
| :--- | :--- |
| `main.go` | `assetserver.Options.Handler = webServer.Handler()` — `main.go` already imports `assetserver` |
| `main.go` | route on `Status.Ready` via `assetserver.Middleware` |
| `app.go` | when books open, build the MariaDB `web.Books` and expose the handler |

**The constraint that shapes it:** `assetserver` tries `Assets` **first**, so
`GET /` resolves to `frontend/dist/index.html` — the Vue shell shadows the
dashboard. And the Vue shell owns the connection gate: no connection, no books, no
dashboard. So the front door is **conditional, not static** — no connection → the
connection wizard; books open → the dashboard. Exact middleware mechanics to be
confirmed against Wails v2.16 at implementation time.

**Acceptance evidence:** `wails build`, launch `FinGo.exe` against the dev
database, land on the dashboard, and check the four figures against a direct
`SELECT` on MariaDB.

**Then, as its own refactor slice (zero new behaviour):** retire the duplicate —
`practice.Client.TrialBalance`, `App.TrialBalance`, and the trial-balance panel in
`App.vue`. `app.go:504` is the only caller. Regenerating `frontend/wailsjs`
bindings comes with it.

## Order, and why

```
1  MariaDB ledger source ──► 3a reports behind the port ──► dashboard figures are real
2  VAT rate table ─────────► 3d Settings
3b, 3c chart and documents
4  mount in Wails ─────────► the desktop app's front door
```

1 → 3a is the shortest path to a dashboard that does not forget. 2 is needed only
by 3d. 4 comes last **because mounting a dashboard whose figures vanish on restart
is worse than having none.**

## Deliberately not in this plan

- **`client.Scope` on repositories.** ADR 0003 requires it; no repository takes one
  yet. The desktop app is one client per database by construction. It stays a
  dedicated wide refactor, landed green before anything is built on top.
- **Client switching and authorisation.** `internal/client` has no MariaDB
  `Registry`, and `client.Middleware` is unwired. ADR 0004 says the same.
- **Authentication.** There is no login.
- Opening balances, and the other fifteen business events.

## The biggest risk

**Slice 3c.** `web`'s `CreateInvoice` takes a **free-text customer** and a
`VATRateID`; `internal/trading` and `usecase/sales` expect a `PartnerID` and a
warehouse. Reconciling those is a domain decision, not a mechanical adapter — the
free-text customer exists because there is no partner directory wired. Expect that
one to need its own plan, or an ADR, rather than a quiet adapter.

## Approval

Approving this approves the four slices' shapes and the seams between them, not a
licence to improvise inside them. Each slice re-enters through the gate if its
plan breaks mid-flight.
