# FinGo — Financial Data Review

**Reviewer lens:** Chief accountant, 20 years in trading SMEs (imports, inventory, multi-currency, margin compression, cash-cycle risk).
**Scope:** every module, service, and flow in the repository that touches financial data.
**Method:** full read of `fingo/` — 14 domain packages, `pkg/logger`, sqlc adapter, migration `00001`, `main.go`, `app.go`, frontend bindings, all 22 tests. Read-only.
**Baseline verified at review time:** `go build ./...` clean, `go vet ./...` clean, `go test ./...` 22/22 pass.

> ## ⚠️ LEGAL BASIS SUPERSEDED — READ BEFORE RELYING ON ANY STATUTORY FINDING
>
> This review was written from model recall, not source documents. Its **engineering findings hold** — the entry-model defect, the unfalsifiable balance check, missing COA, absent transactions, no COGS are all arithmetic and control failures that no regime change affects.
>
> Its **statutory findings are out of date.** Verified against primary sources on 2026-10-08:
>
> - **Circular 99/2025/TT-BTC** replaced Circular 200/2014 from FY2026. Circular **133/2016 survives** (amended by TT 46/2025) — the repo's default is valid, merely un-amended.
> - **The whole tax-administration layer was replaced on 01/07/2026**: Luật Quản lý thuế 108/2025/QH15 · NĐ 252/2026 · NĐ 254/2026 · TT 91/2026 · return forms under **TT 89/2026**.
> - **PIT deductions are 15,500,000 / 6,200,000**, not the 11,000,000 / 4,400,000 cited below, and the brackets fell from **7 to 5**.
> - **E-invoice cancellation ("hủy") has been abolished**; only adjustment and replacement remain.
> - **Circular 48/2019/TT-BTC expires ≤ 31/12/2026.**
>
> **Corrections to this document are pending.** The authoritative, sourced register is [`legal-basis.md`](legal-basis.md). Where the two disagree, **legal-basis.md governs.**
>
> Known error in this document: it cites **"S07a-DN (Sổ quỹ tiền mặt)"**. Wrong — cash book is **S07-DN**; S07a-DN is "Sổ kế toán chi tiết quỹ tiền mặt". This was already so under Circular 200, so it is a reviewer error, not a change in law.

| Module | Finding | Severity | Risk | Recommended Fix |

| General Ledger | `voucher_lines` stores one `debit_account_id` + one `credit_account_id` + one shared `amount` (`gl.go:21`). Entries with N debits or N credits cannot be represented. A VAT sales invoice (Nợ 131 110 / Có 511 100 / Có 33311 10) has no encoding: the pair model forces `(131,511,110)+(131,33311,10)` → debit 220, credit 110. | Critical | The most common transaction in a trading SME cannot be booked. Revenue, receivable and output VAT cannot coexist on one invoice. Financial statements cannot be produced from this schema at all. | Migration `00002`: replace the pair columns with one row per account movement — `account_id VARCHAR(36) NOT NULL`, `side ENUM('DEBIT','CREDIT') NOT NULL`, `amount DECIMAL(19,0) NOT NULL`. Drop the two FKs and add one FK to `accounts(id)`. Regenerate sqlc, then rewrite `VoucherLine` and `AddLine` to take account + side + amount. |
| General Ledger | `Voucher.ValidateBalance` (`gl.go:59`) only checks that each line's amount > 0 and both account IDs are non-empty. Debit and credit per line are the same number by construction, so `SUM(Debit) == SUM(Credit)` can never fail. | Critical | A structurally unbalanced or fabricated voucher passes validation. The core double-entry control does not exist, so no downstream figure can be trusted. | After the line-shape change above, accumulate two `decimal.Decimal` totals over the lines — sum `amount` where side is DEBIT, sum `amount` where side is CREDIT — and return an error unless `totalDebit.Cmp(totalCredit) == 0`. Follow the existing house pattern in `report.go:48`. Call it in `SaveVoucher` and again immediately before posting. |
| General Ledger | No chart of accounts exists anywhere. Account codes appear only as literal strings inside test files (`"1111"`, `"5111"`). `CreateAccount` (`db/queries/gl.sql:12`) is never called. | Critical | `voucher_lines.debit_account_id` and `credit_account_id` are foreign keys into an empty `accounts` table, so not one voucher can be inserted. The application can never record a transaction. | Add a seed migration inserting the statutory COA with sub-accounts in use by trading SMEs (1111, 1121, 131, 1331, 1388, 152, 153, 1561, 211, 2141, 242, 331, 33311, 3334, 334, 3382-3386, 411, 4211, 4212, 5111, 515, 5211-5213, 632, 635, 641, 6422, 711, 811, 911), tagged by TT133 vs TT200. Add a startup guard that refuses to post when `ListActiveAccounts` returns empty. |
| Persistence | Voucher creation is not transactional. `CreateVoucher` (`db/queries/gl.sql:16`) and `CreateVoucherLine` (`:20`) are separate `:exec` statements. `Queries.WithTx` (`sqlc/db.go:27`) exists but has no caller. | Critical | A failure between the header insert and the line inserts leaves a header with no lines, or a partial line set — an unbalanced voucher permanently in the ledger. Any mid-batch error silently corrupts the books. | Build a `gl` repository that opens `db.BeginTx`, calls `queries.WithTx(tx)`, inserts the header and every line, then commits. Never expose the header and line inserts as independent calls to callers. |
| Persistence | No database connection exists. `sqlc.New` (`sqlc/db.go:19`) is never called, there is no `sql.Open`, no DSN, no pool, no migration runner. `go-sql-driver/mysql` is still marked `// indirect` in `go.mod`. Only 4 tables exist (`accounts`, `accounting_periods`, `vouchers`, `voucher_lines`); 13 of 14 domains have no table. | Critical | Nothing persists. Every domain struct is a value that lives and dies in memory, and 13 domains cannot be stored at all. | Add a `mariadb` adapter owning `sql.Open` + pool tuning, wire `sqlc.New(db)`, embed goose migrations and run them at startup, and add the missing tables (partners, items, warehouses, invoices, stock, employees, assets, tax, audit) with their repository implementations. |
| Sales | `SalesInvoice` has no cost of goods sold. Nothing posts Nợ 632 / Có 156, and `Item.COGSAccount` (`catalog.go:59`) is declared and never read. | Critical | Gross margin — the number a trading SME is managed on — is uncomputable, and TK 632 is understated while TK 156 is overstated. The P&L is wrong by the entire cost of everything sold. | On posting a sales invoice, resolve each line's cost from the inventory valuation service and generate Nợ 632 / Có 156 for the total. Persist `COGSAmount` on the invoice so margin is reportable without recomputation. |
| Inventory | No inventory valuation engine exists. `StockMovementLine` (`inventory.go:10`) carries no cost layer and no running balance. The FIFO, perpetual moving-average and periodic weighted-average methods described in the README are entirely absent. | Critical | TK 156 and TK 632 carry no defensible value, so both the balance sheet and the P&L are misstated. Perpetual moving average is the default method for Vietnamese trading SMEs; without it no closing figure can be produced. | Add a cost-layer table (`item_id`, `warehouse_id`, `received_at`, `qty_in`, `qty_remaining`, `unit_cost`) and an outbound costing service implementing perpetual moving average as the default, with FIFO selectable per item. Every stock-out consumes layers and returns a unit cost. |
| Tax | The VAT declaration cannot see input VAT. `PurchaseInvoiceLine.VATRate` (`purchase.go:16`) is never used; `PurchaseInvoice` exposes only `Subtotal()` (`:19`) and `CalculateSubtotal()` (`:47`), both net-only. | Critical | Deductible input VAT (TK 1331, chỉ tiêu 23-25 of form 01/GTGT) is always zero, so VAT payable is overstated every period. Filing the declaration is tax non-compliance. | Add `VATAmount()` and `Total()` to `PurchaseInvoiceLine` mirroring the sales implementation, aggregate deductible input VAT by rate, and feed chỉ tiêu 23-25. Only VAT on invoices that meet the deduction conditions may be included. |
| Tax | Corporate income tax is not modelled. There is no CIT calculation, no provisional quarterly payment, and no TK 821 / TK 3334 posting anywhere in the repository. | Critical | Income tax expense and the tax liability are absent from the accounts, so profit after tax is overstated and the provisional quarterly filings required of the company cannot be supported by any figure the system holds. | Add a CIT engine computing taxable profit from accounting profit with the standard adjustments (non-deductible expenses, exempt income, loss carry-forward), post quarterly provisional amounts as Nợ 8211 / Có 3334, and reconcile the annual finalisation against the provision. |
| Payroll | Personal income tax is never calculated. `PIT` is a field initialised to `decimal.Zero` (`payroll.go:31`) and merely subtracted in `CalculateNetSalary` (`:49`). No progressive bracket function exists in the repository, and `Employee.NumberOfDependents` (`:17`) is never read. | Critical | TNCN is never withheld, so net pay is overstated and the employer is exposed to under-withholding penalties and interest. The README and project brief both claim this is implemented. | Implement a progressive PIT service: taxable income = gross − employee insurance (on the capped insurable base) − personal deduction − dependents × dependent deduction; apply the current statutory bracket table; round to đồng. Re-verify the deduction amounts against current law — the 11M/4.4M figures cited in the README are the superseded schedule. |
| Payroll | Statutory employer contribution rate is wrong and self-contradictory. The code applies 21.5% (`payroll.go:43`); its own comment on the preceding line says 17+3+1+2 = 23%; the README says 23.5%. The 10.5%/21.5% are applied to `GrossSalary`, but the legal base is the insurable salary, and BHXH/BHYT are capped at 20× lương cơ sở while BHTN is capped at 20× regional minimum wage. | Critical | Payables TK 3383/3384/3386/3382 are misstated every payroll run and the employer under-contributes, which is a compliance exposure with the social insurance authority. The comment, the code and the documentation disagree, so the intended behaviour is not even knowable. | Replace the single literal with an itemised, configurable table — BHXH 17.5%, BHYT 3%, BHTN 1%, KPCĐ 2% — each applied to the insurable salary rather than gross, with BHXH/BHYT capped at 20× lương cơ sở and BHTN at 20× minimum wage. Make KPCĐ applicability depend on headcount. Reconcile the comment and the README to one source of truth. |
| Reporting | No statutory financial statements exist. `report` contains a `TrialBalance` struct, a three-value `FinancialReportType` enum, and a repository stub. B01-DN, B02-DN and B03-DN are not implemented — no chỉ-tiêu mapping and no formulas. There is also no Sổ Nhật ký chung, Sổ Cái, or Sổ quỹ output. | Critical | The company cannot produce the statements it is legally required to file, and cannot print the statutory books. The application cannot discharge its core purpose. | Implement a report engine with an explicit chỉ-tiêu definition table (indicator code → account ranges → formula → sign) for B01-DN, B02-DN and B03-DN under the selected circular, plus book outputs S03a-DN, S03b-DN and S07a-DN. Drive every figure from posted vouchers only. |
| System | Vouchers carry no user attribution and no audit trail is persisted. `vouchers` (`migration:33-42`) has no `created_by` or `posted_by` column. `AuditLog` (`system.go:56`) has no table and no implementation; `LogAudit` (`:92`) is a stub. `NewUserStub` uses local `time.Now()` (`:73`). | Critical | Nobody can demonstrate who created, changed, posted or voided an entry. The books cannot be attributed or defended in a tax audit, which fails the record-keeping requirements of the circulars the app claims to implement. | Add `created_by`, `posted_by`, `voided_by` (UUID FK to `users`) and UTC `created_at`/`posted_at` to `vouchers`; create an append-only `audit_log` table with no UPDATE/DELETE grants, storing user, machine, UTC timestamp and before/after payload; write to it inside the same transaction as every posting, void and master-data change. |
| Inventory | No inventory write-down or obsolescence provision. There is no model for dự phòng giảm giá hàng tồn kho (TK 2294) and no cost against net-realisable-value comparison. | High | Slow-moving and obsolete stock sits at cost on the balance sheet indefinitely, overstating inventory and equity while understating expense. Year-end provisioning is a statutory requirement and is entirely unrecorded. | Add a per-item provision entity holding cost, net realisable value and provision amount, with a year-end run posting Nợ 632 / Có 2294 and a reversal carried into the following period. |
| Sales | No rounding to đồng anywhere in the repository. `VATAmount()` (`sales.go:23`) multiplies a rate and returns a fraction, and `CalculateTotal()` (`:58`) sums unrounded line totals. | High | VND has no subunit, so every invoice carries fractional đồng. Line-level rounding that does not sum to the invoice total leaves the AR subledger disagreeing with the ledger, and the discrepancy compounds across thousands of invoices. | Introduce a money helper that rounds half-up to 0 đồng at a defined granularity, round each line's VAT amount once, derive the invoice VAT as the sum of rounded line VAT, and store integer đồng amounts. Change `amount` to `DECIMAL(19,0)`. |
| Sales | No returns, credit notes or revenue deductions. `SalesInvoiceLine` (`sales.go:10`) has no discount field, and there is no model for hàng bán bị trả lại or giảm giá hàng bán (TK 5211/5212/5213). | High | Revenue is overstated and never corrected by the normal trading workflow. Returns are routine in distribution, so the cumulative overstatement grows with volume. | Add a credit-note document with a `references_invoice_id`, posting the reverse of the original (Nợ 521 / Nợ 33311 / Có 131) and returning goods to stock at original cost. Add line-level and invoice-level discount fields feeding TK 5211. |
| Sales | Revenue is recognised at `InvoiceDate` only. `NewSalesInvoiceStub` (`sales.go:42`) sets `DueDate` to a hardcoded `date.AddDate(0, 0, 30)`. There is no delivery gate, no service-completion gate, no deferred revenue, and no per-customer payment terms. | High | Revenue can be recognised before the performance obligation is satisfied — goods not yet delivered, or prepayments held for future delivery counted as revenue. Recognised revenue is misstated in the period. | Separate order, delivery and invoice events; recognise revenue on delivery or service completion, not invoicing; post customer prepayments to TK 131 credit or TK 3387 and release on fulfilment; add payment-terms fields on the customer and derive `DueDate` from them. |
| Sales | No currency or exchange rate on any sales document. `CompanyProfile.CurrencyCode` (`system.go:51`) exists but no invoice carries a currency or rate, so foreign-currency amounts are treated as if 1:1 with VND. | High | An importer's foreign-currency revenue is recorded at the wrong base amount, misstating revenue, receivable and any FX difference. The target user does multi-currency by definition. | Add `currency_code` and `exchange_rate` (with the rate source and effective date) to invoices and their journal lines; store the VND base amount alongside the transaction amount; implement period-end revaluation of monetary balances to TK 413. |
| Purchase | No landed-cost allocation. Import freight, customs duty, and clearance charges have no model, so the cost of imported goods cannot include them. | High | Inventory cost is understated and COGS follows it down, overstating margin on every imported consignment. Duty is also a real cash cost that goes unrecorded against inventory. | Add a landed-cost document with a cost-type enum (freight, insurance, duty, clearance) that allocates to the target stock-in lines by value, quantity or weight, adding to the inventory cost layer and posting to TK 156 rather than to expense. |
| Purchase | Purchases have no VAT, no payment tracking and no three-way match. `PurchaseRepositoryStub` (`purchase.go:55`) exposes only `SavePurchaseInvoice`. | High | AP balance cannot be aged or reconciled against supplier statements, and input VAT cannot be claimed. Supplier disputes go untracked. | Add VAT computation, an AP allocation model linking payments to invoices, and matching of purchase order, goods receipt and invoice before posting. |
| Cash | No bank reconciliation. `BankTransaction` (`cash.go:39`) carries a `ReferenceNo` and nothing else; there is no statement import, no matching routine, and no unreconciled-items report. | High | The book bank balance drifts from the statement through unrecorded fees, interest and timing differences, and the drift is invisible until it is large. The cash-cycle risk the module exists to control goes unmanaged. | Add statement import keyed on bank account and statement line, an auto-match against book transactions by amount and value date, an exceptions queue for unmatched items, and a reconciliation report proving book to statement with outstanding items listed. |
| Cash | Payments and receipts have no idempotency key. `CashReceipt`/`CashPayment`/`BankTransaction` (`cash.go:10-48`) have no external reference, no uniqueness constraint, and no dedupe check. | High | A retry, a double click, or a re-imported bank statement posts the same cash movement twice. Cash and bank balances become wrong, and the error is invisible until reconciliation. | Require a caller-supplied idempotency key on every payment and receipt, enforce a unique index on it, and reject a second insert with the same key. For bank imports, key on bank account + statement reference + value date + amount. |
| Cash | Receipts and payments are never allocated to specific invoices. `CashReceipt` (`cash.go:10`) carries a `CustomerID` and an `Amount` with no link to invoice documents. | High | AR/AP cannot be aged per invoice, đối chiếu công nợ cannot be produced, and a customer's balance cannot be explained. Settlement of a specific invoice is untraceable. | Add an allocation table (payment doc, invoice doc, allocated amount) and a service that applies a receipt across open invoices by FIFO or by explicit selection, writing off residual differences only with approval. |
| Inventory | `StockOutward` (`inventory.go:27`) has no constructor and no `AddLine`. `AddLine` is defined on `StockInward` only (`:47`). | High | Goods can be received into the system but never issued. The warehouse record and TK 156 diverge immediately, and no sale can relieve stock. | Add a `NewStockOutwardStub` constructor and a symmetric `AddLine`, and require every stock-out to consume a cost layer so a COGS value is produced. |
| Reporting | No doubtful-debt provision or write-off. There is no ageing-driven provision model (TK 2293) and no bad-debt write-off path. AR ageing, which would drive the provision, is claimed in the README and is itself unimplemented. | High | Receivables are carried at full face value indefinitely, overstating assets and profit, and uncollectible balances are never written off, so the AR subledger never reflects what is actually collectable. | Implement an ageing engine over invoice-level payment allocations, apply the statutory provision bands for overdue receivables to compute TK 2293, and provide an approval-gated write-off posting to TK 642 against that provision. |
| Tax | E-invoice lifecycle does not model adjustments or replacements. `EInvoiceStatus` (`tax.go:17`) offers Draft/Signed/Submitted/Approved/Rejected/Canceled, with no linkage for hóa đơn điều chỉnh or hóa đơn thay thế, and `EInvoice.VoucherID` (`:30`) is the only tie to the ledger. | High | A corrected invoice cannot be represented without losing the audit chain to the original. Tax authority reconciliation will not tie out, and the ledger will disagree with issued invoices. | Add `adjusts_invoice_id` and a replacement/adjustment type to `EInvoice`, keep both documents immutable, and post the adjustment entry against the original period or the current one per the applicable rule. |
| System | There is no document approval workflow. `Voucher` (`gl.go:31`) offers only `IsPosted`, and invoices likewise; there is no draft→submitted→approved→posted state machine, no approver field and no rejection path, although the README describes exactly that lifecycle. | High | Nothing must be approved before it reaches the ledger. Any user can post an erroneous or fraudulent entry directly, and no record exists of who authorised it. | Add an explicit document status enum with the permitted transition graph, an approver identity and UTC timestamp on each transition, a role check per transition, and an audit entry written in the same transaction as the state change. |
| Fixed Assets | Depreciation never stops. `CalculateMonthlyDepreciation` (`asset.go:42`) divides original cost by useful life with no ceiling, and `AccumulatedDep` (`:15`) is never updated by any function in the repository. | High | An asset keeps being depreciated past the end of its useful life, so TK 214 exceeds TK 211 and expense is overstated in every later period. The register cannot report net book value. | Cap the charge at `OriginalCost − AccumulatedDep`, return zero once fully depreciated, and make the depreciation run update `AccumulatedDep` transactionally with the Nợ 642 / Có 214 entry. |
| Fixed Assets | No tools-and-equipment (CCDC) or prepaid-expense path. The README claims monthly allocation for TK 242 and the `catalog.Item` model has a `TOOL` type, but `asset` models only fixed assets. | High | Small tools and prepaid costs are either expensed immediately (misstating the period) or held in TK 153 forever with no allocation. Both misstate the P&L. | Add a CCDC/prepaid entity with allocation period, start month and remaining balance, generating monthly Nợ 642 / Có 242 entries, plus a threshold rule routing low-value purchases away from TK 211. |
| Period Closing | Closing does not generate entries. `CalculateNetProfit` (`closing.go:57`) subtracts expense totals from revenue totals and returns a number; there is no 911 clearing, no 4211/4212 split, and the revenue set (`:32`) omits TK 521. | High | Revenue deductions are never cleared, so 911 nets incorrectly and profit carried to TK 421 is wrong. The closing is a calculation, not a posting, so the ledger is never actually closed. | Generate the closing vouchers: kết chuyển 511/515/711 and 521 to 911, then 632/635/641/642/811 to 911, then the 911 residual to 4212 if profit or 4211 if loss — all as posted, reversible vouchers. |
| Period Closing | The lock does not protect posted data. `SystemLockConfig.CheckVoucherDateAllowed` (`closing.go:15`) is only a date test; nothing prevents editing, voiding or re-dating an already-posted voucher, no per-module lock exists, and there is no override path for the chief accountant. | High | Prior-period figures can be changed after they have been reported, silently destroying comparability and auditability of filed statements. | Enforce immutability on posted vouchers at the repository layer; require a reversal document instead of an edit; add per-module lock dates; expose an override that requires the chief accountant role and writes an audit entry. |
| General Ledger | Voucher numbers are globally unique. `voucher_no VARCHAR(64) NOT NULL UNIQUE` (`migration:35`) means no per-book series (PT/PC/BN/BH), no fiscal-year reset, and no gap detection. | High | Statutory books cannot be numbered in the conventional series, numbers cannot restart each year, and a missing number cannot be detected — which is exactly what a tax audit checks. | Move uniqueness to a composite key on (book/series, fiscal year, number), add a numbering service issuing the next number inside the posting transaction, and report gaps rather than silently allowing them. |
| General Ledger | Posted vouchers are mutable. `Voucher.IsPosted` (`gl.go:38`) is a plain settable bool with no guard, no `posted_at`, no `posted_by`, and no reversal function — although the README claims `CreateReversal`. There is no journal listing query either. | High | Any posted entry can be altered in place with no trace and no reversing entry, so the audit trail is fiction and prior-period figures are unprotected. | Make posting a one-way transition: store `posted_at`/`posted_by`, reject updates to posted rows, and provide `CreateReversal` producing a mirrored voucher referencing the original. Add a journal query ordered by date for Sổ Nhật ký chung. |
| System | No authentication and no password hashing. `User.PasswordHash` (`system.go:22`) is a bare string; there is no bcrypt or equivalent import, no hash function, and no verification path. | High | Anyone with file or network access to the database can read and alter financial data, and passwords cannot be handled safely at all. Roles are defined but meaningless without a verified identity. | Add password hashing (bcrypt or argon2id) with a cost parameter, a login flow issuing a session, and reject all financial operations lacking an authenticated principal. |
| System | Segregation of duties is not enforced. `Permission.Action` (`system.go:40`) lists POST and UNPOST and six roles are defined (`:10-17`), but no code checks any role, and nothing prevents the person who creates a voucher from posting or voiding it. | High | A single user can create, approve, post and void any entry, which defeats the primary internal control over the ledger and permits undetected fraud. | Add an authorization check on every mutating operation keyed by module and action, and enforce that the creator cannot be the poster for post and void operations. Reject and audit any attempt. |
| Opening Balances | Opening balances are not tied out to sub-ledgers. `ValidateBalance` (`opening.go:70`) checks only that account totals balance; nothing requires customer openings to equal TK 131, vendor openings to equal TK 331, or inventory openings to equal TK 156. `IsLocked` (`:47`) is never enforced. | High | Books open in balance while every sub-ledger disagrees with its control account. The error surfaces months later, after returns have been filed, as an unexplainable AR or inventory difference. | Extend validation to reconcile each sub-ledger to its control account and reject the batch on any difference; enforce `IsLocked` so openings cannot be edited once posting begins; require the opening batch to be approved before the first voucher posts. |
| Reporting | `TrialBalance` (`report.go:21`) is the only report. It has no opening-balance derivation, no netting rule, no account-detail drill-down, and no check for balances on the wrong side of an account's nature. | High | A trial balance can be produced that sums correctly yet shows impossible balances (a credit balance on a debit-nature account), and there is nothing to drill into when it does not tie out. | Derive opening balances from the prior period close, net each account to a single closing figure by nature, validate the balance against `accounts.nature`, and expose a drill-down from each row to its vouchers. |
| System | No intercompany or related-party model. No entity concept exists beyond the single `CompanyProfile` (`system.go:44`), so transactions between related entities cannot be flagged, matched or eliminated. | Med | Balances between related parties cannot be reconciled or eliminated, and related-party disclosures cannot be produced. | Add a counterparty entity reference and an intercompany flag on documents, plus a per-counterparty reconciliation view that must net to zero across the group before a period can close. |
| Inventory | `StockMovementLine.ID` is fabricated as `itemID + "-line"` (`inventory.go:49`). | Med | Two lines for the same item on one ticket receive an identical ID, so the second overwrites or collides with the first. | Generate a UUID per line, or key on (ticket id, item id, line order) and make the pair unique. |
| Inventory | No stock card, no nhập-xuất-tồn report, and no TK 611 periodic-inventory path despite the README. | Med | Warehouses cannot be operated or reconciled to the ledger without external spreadsheets. | Add stock-card and movement reports per item and warehouse, and support the periodic method where purchases and issues clear through TK 611 at period end. |
| General Ledger | `AddLine` (`gl.go:54`) silently overwrites `LineOrder` with the append index. ## Summary

The model is a document register, not a ledger. Three conditions gate everything else:

1. **Entries must express one-to-many and many-to-one**, or no VAT invoice, no landed cost and no multi-line purchase can exist.
2. **A posted document must produce a balanced voucher atomically**, or nothing downstream can be trusted.
3. **A chart of accounts must exist and the application must reach its database**, or no transaction can be recorded at all.

Every Critical finding above reduces to one of those three, or to a statutory calculation (PIT, insurance, input VAT) that is absent or wrong.
